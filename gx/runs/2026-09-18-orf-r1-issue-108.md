**Severity: high — a 603-residue gene reported as a 128-residue fragment, from a default call, with nothing in the response saying which genetic code was used.** Every mitochondrial, bacterial, plastid, yeast and ciliate record is affected. "Mitochondrial DNA" is not an exotic input for a gene-editing desktop app.

Found by the Rockin-Robin `oligolia-gx-tests` contract, ORF/translation round 1, against commit `8424c4d`.

## Requirement

**OR-13** — *The ORF finder can be asked for a non-standard genetic code. NC_012920.1 declares `/transl_table=2` for all 13 of its CDS features; its MT-ND5 gene is one continuous 603-residue reading frame under table 2 but is interrupted by 11 internal TGA codons, which table 2 reads as tryptophan and table 1 reads as stop. Given MT-ND5's bases and table 2, the finder must report one ORF of 603 residues.*

## Root cause

`backend/routers/analysis.py:499`

```python
def find_orfs(sequence: str, min_length_aa: int = 30, include_all_starts: bool = False) -> ORFFindResult:
```

There is no genetic-code argument. `GENETIC_CODE` (`backend/routers/analysis.py:382`) is a module-level table-1 dict with no alternative and no parameter reaching it, and `find_orfs` reads it directly at `backend/routers/analysis.py:517` (`aa = GENETIC_CODE.get(codon, "X")`).

The app is **not** uniformly table-1-only, which is what makes this a gap rather than a scope decision:

- `backend/services/annotations.py:83-86` reads `/transl_table` off the feature itself and honours whatever NCBI table it names.
- The app's GenBank reader parses those qualifiers, so the record's declared code is already in memory when the user runs Find ORFs.

So a user can load NC_012920.1, see `/transl_table=2` on all 13 CDS features in the Annotations view, run Find ORFs on the same record, and get a table-1 answer — with nothing in `ORFFindResult` (`backend/routers/analysis.py:120-124`: `sequence_length`, `min_length_aa`, `orfs`, `total_found`) naming the code that produced it.

## Traced to

- `backend/routers/analysis.py:499` — the signature, which has no table parameter (the run record cites `:497`).
- `backend/routers/analysis.py:382` — `GENETIC_CODE`, a single table-1 dict with no sibling and nothing selecting it.
- `backend/routers/analysis.py:120-124` — `ORFFindResult`, which has no field naming the code used, so the answer is not even self-describing.

## Structural note — the round's main finding

**The app has two translation paths, and only one of them reads the record.**

`backend/services/annotations.py:66-92` (`restated_translation`) reads `/transl_table` off the feature and honours every NCBI table, and handles a ragged trailing codon by trimming before it translates. `find_orfs` does neither: hard-coded table 1, and a run-off interval that carries untranslated bases (see the sibling partial-CDS issue). That contrast is the shape of the fix — the two paths should converge on one table-aware translator rather than each growing its own. This issue, the start-codon-set issue, and the run-off/partial issue are all instances of `find_orfs` not having access to what `restated_translation` already has.

This is a missing capability, not a miscalculation: the endpoint's signature gives a caller no way to declare the code, so the sealed test asserts against an absent parameter and will keep failing until the subject grows one. Its premise, though, is a recorded NCBI literal — the 603-residue `/translation` — not a judgement call.
