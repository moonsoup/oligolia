**Severity: high — one molecule, two different gene contents, depending on an editorial choice about where the flat file starts.** pUC19 is the plasmid this app ships as its own fixture and *bla* is its selectable marker: the single most-looked-for gene on it disappears when the record's origin falls inside it, and what appears in its place is a plausible-looking shorter fragment of the same protein.

Found by the Rockin-Robin `oligolia-gx-tests` contract, ORF/translation round 1, against commit `8424c4d`.

## Requirement

**OR-12** — *On a circular molecule the ORF set does not depend on where the record happens to start. pUC19 is a 2686 bp circular plasmid whose bla gene is a complete 286-residue ORF at top-strand `[1625:2486)` in frame -3. Rotating the origin into the middle of that gene must not lose it: the multiset of reported protein strings must be identical for the unrotated molecule and for rotations of 1700, 2000 and 2400 bases.*

## Root cause

`backend/routers/analysis.py:499`

```python
def find_orfs(sequence: str, min_length_aa: int = 30, include_all_starts: bool = False) -> ORFFindResult:
```

No topology argument, and the frame walk at `backend/routers/analysis.py:509-547` runs each frame linearly from index 0 to the end of the string. An ORF that crosses the origin is truncated at the break — one part of it ends at the last codon before the end of the string, the other starts somewhere after index 0, and neither is the gene.

The app represents circularity everywhere else:

- `Sequence.is_circular`, carried through every edit operation (#96 tracks the one place it is dropped).
- `/primers/digest` already reports circular fragments.
- The pinned pUC19 record is GenBank L09137.2, circular.

So a circular molecule is a thing this app models, stores, edits and digests — and then cannot analyse for ORFs.

## Differential evidence

Input: `gx/corpus/inputs/puc19_L09137.2.txt` — pUC19, 2686 bp, circular, sha256 `356116fd7a575f5bf71f6f4cf25059fe049bd72566816691630d423dd9ab329b`. Call: `find_orfs(bases, min_length_aa=30)`. The rotated input is `bases[offset:] + bases[:offset]`, which is the identical molecule read from a different base; each of the three offsets lands strictly inside `1625 < offset < 2486`.

Oracle: the subject's own answer for the unrotated record. A rotation is the identity on a circle, so no second finder is needed — and OR-7 has already pinned that unrotated answer, field for field, against an independent finder written from gc.prt. `test_or_12_bla_is_a_complete_orf_in_the_unrotated_record` states the premise separately and **passes**: there is exactly one ORF at `[1625:2486)`, frame -3, 286 aa.

## Traced to

- `backend/routers/analysis.py:499` — the signature, which gives a caller no way to declare circularity (the run record cites `:497`).
- `backend/routers/analysis.py:509-547` — the linear frame walk, `while i + 3 <= len(strand_seq)`, which stops at the string's end rather than wrapping.
- `backend/routers/analysis.py:120-124` — `ORFFindResult`, which has no field that could express an origin-spanning interval either.

## Note on severity and shape

This is a **missing capability** rather than a miscalculation — the endpoint cannot be *asked* for a circular read — so the sealed tests assert against an absent parameter and will keep failing until the subject grows one. But the observable behaviour is not "unsupported": it is a 200 response reporting a different set of genes for the same molecule, with no warning. A fix also has to decide what interval to report for an ORF that wraps (an `end < start` interval, or one past `len(seq)`), which is why the rotation-invariance test deliberately asserts on proteins only and leaves that convention to the implementer.
