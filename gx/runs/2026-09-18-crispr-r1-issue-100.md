Found by the `oligolia-gx-tests` differential round on CRISPR (round 1). Not fixed here — this is a report, with a sealed failing test attached.

## Symptom

Load COL1A1 (NG_007400.1, 24,544 bp), pick **LwaCas13a**, design. The panel's
status line says:

> 10 guides shown (of 24,523 candidates) for 24544 bp target

All ten are the same place. Their positions are `[10, 11, 14, 15, 16, 17, 18, 20, 23, 24]` —
ten 22-mers packed into a 46-base stretch at the very 5' end of a 24.5 kb gene,
total span 14 nt. Every pair overlaps. The user is told the app searched 24,523
windows and is then shown one target window in ten shifted copies, with no
indication that the other 24,500 were all equally ranked and discarded by list
order.

pUC19 is the same shape: positions `[5, 8, 9, 11, 12, 14, 16, 17, 19, 20]` out of
2,665 candidates.

## Requirement

**CR-10** (`gx/crispr/register.json`):

> `max_guides` must select among the candidates, not collapse onto one locus. When the app searches a full-length input and reports thousands of candidates but shows the user only max_guides of them, the shown set must contain at least two mutually non-overlapping sites — otherwise the panel reports 'N guides shown (of M candidates)' while in fact offering one target window in max_guides shifted copies. Pinned as the sharpest case: LwaCas13a on the 24,544 bp COL1A1 record searches 24,523 windows.

Overlap definition, pinned in the register: two guides overlap when
`abs(pos_a - pos_b) < guide_length`. The requirement asks for **one**
non-overlapping pair out of the 45 pairs in a 10-guide set.

## Where it is

Three lines in `backend/routers/crispr.py`:

- `backend/routers/crispr.py:185` — the Cas13 branch's on-target score is
  `round(0.5 + (0.1 if 40 <= gc <= 60 else 0.0), 3)`. It takes exactly **two** values,
  0.5 and 0.6.
- `backend/routers/crispr.py:190` — the sort key is
  `(-(g.on_target_score or 0), abs((g.gc_content or 0) - 50))`. A 22-mer with 11 G/C
  has `gc_content` exactly `50.0`, so for every 50%-GC window the tie-break term is
  `0.0` **as well**.
- `backend/routers/crispr.py:191` — `guides = guides[:req.max_guides]`.

Every 50%-GC window is therefore fully tied on both key components. Python's sort
is stable, so the surviving order is insertion order, which for the Cas13 branch
(`backend/routers/crispr.py:176`, `for i in range(0, len(target) - guide_length + 1)`)
is ascending position. The user gets the first ten 50%-GC windows in the molecule,
wherever the molecule happens to start.

GUI side: `gui/panels/crispr_panel.py:185` is the status line that reports
"N guides shown (of M candidates)".

## Why this is a defect and not a tuning preference

The sort key is not wrong because it prefers 50% GC. It is wrong because it is
**constant over the candidate set**, so `max_guides` stops being a selection and
becomes a slice of the scan order. Two independent things would each fix it:

1. a ranking key with enough resolution to separate 24,523 candidates (see the
   sibling issues on the on-target score), and/or
2. an explicit spacing/diversity constraint on the shown set — pick the best guide
   in each window, or refuse to show two guides closer than `guide_length`.

(2) is the one that holds regardless of what the score becomes, and is what CR-10
actually asserts.
