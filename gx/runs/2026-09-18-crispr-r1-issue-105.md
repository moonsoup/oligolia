Found by the `oligolia-gx-tests` differential round on CRISPR (round 1). Not fixed here — this is a report, with a sealed failing test attached.

## Symptom

`/crispr/design` refuses a target containing anything outside `ACGTN`, with
`400 Target sequence must be DNA (ACGTN only)`. Its sibling `/crispr/score_guide`
takes the same alphabet and answers **HTTP 200 with a confident verdict**:

| guide handed to `/crispr/score_guide` | response |
|---|---|
| `ACGTACGTACGTACGTACGU` (an RNA-written crRNA) | `200` · recommendation **"Good"** · `on_target_score` 0.6 · `gc_content` 50.0 |
| `ACGTACGTACGTACGTACG!` | `200` · **"Good"** · 0.6 · 50.0 |
| `ACGTACGTACGT12ACGTAC` | `200` · **"Good"** · 0.63 · 45.0 |
| `ACGTACGTACGTACGT\tACG` (tab) | `200` · **"Good"** · 0.62 · 50.0 |

One capability, two endpoints, two different verdicts on an input that is not a
sequence. Directly the family that #87 closed for the primer/restriction endpoints
(fixed in `17554c6`) and that #92 tracks for PCR primer design.

The `U` case is the one most likely to reach a real user: pasting an RNA-written
crRNA into a guide-scoring box is an ordinary mistake, and the app answers "Good"
instead of saying the input is RNA.

## Requirement

**CR-13** (`gx/crispr/register.json`):

> The two CRISPR endpoints must agree on what is not a sequence. /crispr/design refuses a target containing any character outside ACGTN with HTTP 400 'Target sequence must be DNA (ACGTN only)'. /crispr/score_guide takes a guide of the same alphabet and must refuse the same way, rather than returning HTTP 200 with a GC percentage computed over the non-nucleotide characters and a categorical 'Good'/'Fair'/'Poor' recommendation. Same family as #87: one input, one verdict, across both endpoints of a capability.

A space or a newline is layout, not a character: `/crispr/design` strips both before
validating, and the sealed test does not ask anything else to be rejected. The four
inputs above are characters that are not nucleotides, which is a different thing.

## Differential evidence

Exact inputs (each 20 nt, so the existing 17..24 length guard is not what would
reject them):

```
punctuation  ACGTACGTACGTACGTACG!
rna-u        ACGTACGTACGTACGTACGU
digits       ACGTACGTACGT12ACGTAC
tab          ACGTACGTACGTACGT<TAB>ACG
```

| endpoint | call | result |
|---|---|---|
| `/crispr/design` | `design(puc19[:1000] + <guide>, "SpCas9")` | **400** `Target sequence must be DNA (ACGTN only)` — all four |
| `/crispr/score_guide` | `score_guide(<guide>)` | **200** with a recommendation — all four |

The GC percentages are not merely meaningless, they are arithmetically wrong:
`_gc_content` divides the G+C count by `len(seq)`, so `!`, `U`, digits and the tab
are silently counted as non-G/C *bases*. `ACGTACGTACGTACGTACGU` reports 50.0% over
20 characters when there are 19 nucleotides.

## Where it is

`backend/routers/crispr.py`:

- `:77-78` — the reference behaviour:
  ```python
  if not all(c in "ACGTN" for c in target):
      raise HTTPException(400, "Target sequence must be DNA (ACGTN only)")
  ```
- `:220-221` — `/crispr/score_guide` validates **length and nothing else**:
  ```python
  if len(guide_sequence) < 17 or len(guide_sequence) > 24:
      raise HTTPException(400, "Guide must be 17-24 nt")
  ```
- `:222-223` — then scores and measures the raw string:
  `_doench_rule_set1_score(guide_sequence)` and `_gc_content(guide_sequence)`.
- `:11-13` — `_gc_content` is `(G + C) / len(seq) * 100`, with no alphabet check.
- `:238` — the verdict: `"Good" if score >= 0.6 else "Fair" if score >= 0.4 else "Poor"`.

A 4xx here costs one `if` and matches what the sibling endpoint already does two
hundred lines up in the same file.
