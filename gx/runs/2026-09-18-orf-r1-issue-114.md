**Severity: high — transcribe a sequence in the app, run Find ORFs on the result, and every ORF is gone.** No error, no warning, HTTP 200: a 24.5 kb human gene with 171 ORFs reports zero. An empty result is neither an answer nor a refusal.

Found by the Rockin-Robin `oligolia-gx-tests` contract, ORF/translation round 1, against commit `8424c4d`.

## Requirement

**OR-10** — *RNA input denotes the same molecule as its DNA back-transcription. `find_orfs` on an RNA sequence must report the same ORFs, at the same coordinates, as `find_orfs` on the same sequence with U written T — or refuse the input. It must not return an empty result.*

## Root cause

`backend/routers/analysis.py:501`

```python
seq = sequence.strip().upper().replace(" ", "").replace("\n", "")
```

No `U` → `T`. And `GENETIC_CODE` (`backend/routers/analysis.py:382`) is keyed on DNA codons only — `"TTT"`, `"TTC"`, … — with no RNA spelling anywhere in it.

So on RNA input:

- `AUG` is not in `start_codons` (`backend/routers/analysis.py:507`), so no ORF is ever opened;
- every codon misses the dict and `GENETIC_CODE.get(codon, "X")` at `backend/routers/analysis.py:517` scores `X`;
- the finder walks all six frames of a real transcript and reports nothing.

This is a **first-class input for this app, not an edge case**:

- `backend.models.sequence.MoleculeType.RNA` exists and sequences are stored with it.
- `POST /sequences/{id}/edit` with `operation='transcribe'` (`backend/routers/sequences.py:125-132`) *produces* one — the app hands the user an RNA sequence and then cannot analyse it.
- Biopython registers every table over both alphabets: `unambiguous_dna_by_id` **and** `unambiguous_rna_by_id`. `Bio.Seq.translate` treats T and U identically.

So the user flow is: transcribe in the app → Find ORFs → "0 ORFs found". Nothing says why.

## Traced to

- `backend/routers/analysis.py:501` — the normalisation, which handles no alphabet conversion (the run record cites `:497`/`:499`).
- `backend/routers/analysis.py:382` — `GENETIC_CODE`, DNA-keyed with no RNA spelling.
- `backend/routers/analysis.py:517` — `GENETIC_CODE.get(codon, "X")`, which turns every unrecognised codon into a silent `X` instead of a refusal. That default is why the failure is quiet: the finder never notices it is reading an alphabet it does not know.

## Why this is filed separately from the CRLF/layout issue

Both are `find_orfs` doing its own ad-hoc input handling, but they are **different causes with different fixes**, and the evidence shows it:

`backend/sequence_text.normalize_template` — the app's own single definition of what layout is, which the CRLF issue asks `find_orfs` to adopt — strips `string.whitespace + string.digits` and upper-cases. It deliberately does **not** touch `U`, because `U` is a base, not layout; its docstring is explicit that characters which are not layout are left in place for `validate_template` to refuse. So migrating `find_orfs` to `sequence_text` fixes the carriage returns and leaves this defect exactly as it is. Merging them would hide that.

Note also that `IUPAC_NUCLEOTIDES` in `backend/sequence_text.py:52` does not contain `U`, so if `find_orfs` ever gains `validate_template`'s refusal, RNA input would become a 400 — which satisfies OR-10's "or refuse the input" branch, but is a decision worth making deliberately rather than inheriting. The sealed test accepts either remedy: same ORFs, or an explicit refusal. It does not accept `total_found=0`.
