Found by the `oligolia-gx-tests` differential round on CRISPR (round 1). Not fixed here — this is a report, with a sealed failing test attached.

## Symptom

The CRISPR panel's "On-target" column is produced by a function called
`_doench_rule_set1_score`. Over the 326 real SpCas9 sites in full-length pUC19, the
number in that column agrees with Doench et al. 2014 Rule Set 1 on **9 of 326
sites** and correlates with it at **Spearman rho = 0.2292**. Since that number is
also the primary sort key, nine of the ten guides the panel recommends are not the
ten the cited model recommends.

The app's worst single site: `GACCTGCAGGCATGCAAGCT` (pUC19 position 431, + strand).
Rule Set 1 scores it **0.004**; the app reports **0.690** and paints the row green.

## What is pinned, what is re-typed, and why the name is part of the defect

- **Pinned bytes:** `gx/corpus/crispr/crisporEffScores-v3.1.py` (CRISPOR v3.1),
  sha256 `2b6b589db6e3ef4a2433b3a93e657f2e61235f0ad593aa3007a3cb14e46c12e0`. It
  carries the Rule Set 1 definition: `intercept =  0.59763615`, `gcHigh    = -0.1665878`,
  `gcLow     = -0.2026259`, the 70-entry `doenchParams` table, and the comment
  `Input is a 30mer: 4bp 5', 20bp guide, 3bp PAM, 3bp 5'`.
- **Re-typed, not imported:** `gx/crispr/crispr_oracle.py` transcribes those into
  `DOENCH_INTERCEPT`, `DOENCH_GC_HIGH`, `DOENCH_GC_LOW`, `DOENCH_PARAMS` and
  `doench_rule_set1(mer30)`. The CRISPOR files are reference bytes under a contested
  licence (recorded in `gx/corpus/MANIFEST.json`: the v3.1 tag's LICENSE.txt says
  CC BY-NC 3.0, master's says those files were GPLv3 up to and including 3.1), so
  they are pinned beside the oracle and never imported.
  `crispr_oracle._assert_against_pinned_bytes()` re-parses `doenchParams` out of the
  pinned bytes at import time and asserts it equals `DOENCH_PARAMS` — the
  transcription cannot silently rot.
- **The name is part of the defect, not just the number.** `backend/routers/crispr.py:20`
  says, in the function's own docstring, *"Real RS1 uses logistic regression; this is
  a simplified heuristic"* — so nothing is concealed at the source level. But the
  disclaimer is visible only where it is least needed. What escapes that file is the
  function name `_doench_rule_set1_score`, the response field `on_target_score`, the
  GUI column header "On-target" with no qualifier
  (`gui/panels/crispr_panel.py:112-114`), and the TSV export column `on_target_score`
  (`gui/panels/crispr_panel.py:233`). A user reading "On-target 0.69" in a tool whose
  code calls the function Rule Set 1 has been told something false about provenance,
  independently of whether 0.69 is a defensible heuristic.

## Requirement

**CR-8** (`gx/crispr/register.json`):

> The app names its on-target score after Doench et al. 2014 Rule Set 1 (backend/routers/crispr.py `_doench_rule_set1_score`) and surfaces it to the user as the "On-target" column of the CRISPR panel. A score carrying that name must reproduce the pinned Rule Set 1 definition: intercept 0.59763615, the 70 singleton and dinucleotide weights of `doenchParams`, the GC term abs(10-gcCount) times -0.2026259 (gcCount<=10) or -0.1665878 (gcCount>10), and the logistic 1/(1+exp(-score)), evaluated on the 30mer the model is defined on — 4 nt of 5' context, the 20 nt protospacer, the 3 nt PAM, 3 nt of 3' context. Two consequences are pinned as the failure criteria, so the requirement does not turn on floating-point equality alone: (a) Rule Set 1 depends on the PAM and both flanks, so any score computed from the 20 nt protospacer alone cannot be it; (b) over the 326 SpCas9 sites of full-length pUC19 the app's ordering must agree with Rule Set 1's well enough for max_guides to select the same guides — Spearman rho >= 0.8 and at least 5 of the pinned top 10 shared.

## Where it is

`backend/routers/crispr.py:16-47`, `_doench_rule_set1_score(guide: str)`. It takes a
bare 20 nt protospacer and adds up six hand-chosen single-position preferences
(positions 3, 4, 10, 12, 13, 20), a ±0.1/−0.2 GC-window term, and a −0.15 poly-T
penalty, starting from 0.5.

Called at `backend/routers/crispr.py:112` (plus strand), `:128` (minus strand) and
`:222` (`/crispr/score_guide`).

**The mismatch is structural, not a matter of tuning.** Rule Set 1 is defined on a
30mer and assigns weights to the PAM and both flanks — `DOENCH_PARAMS` entries at
30mer positions 24 and above are PAM/3'-context terms (e.g. `(24,"C",0.28793562)`,
`(27,"G",-0.6890167)`, `(29,"G",0.38634258)`, `(26,"GT",0.11787758)`). The app scores
the protospacer in isolation and has no access to the context at scoring time. No
amount of reweighting makes a protospacer-only function reproduce it.

The two honest repairs:

1. **Compute the pinned model.** The router already has the 30mer in hand at scoring
   time — the plus-strand loop has `target` and `m.start()`, the minus-strand loop
   has `rc_target` and `m.start()` (`backend/routers/crispr.py:108-136`). Extract
   `[pos-4, pos+26)`, apply the real weights, and handle the sites too close to an
   end (Rule Set 1 is undefined there; `crispr_oracle.mer30_for` returns `None`
   rather than inventing bases).
2. **Rename the score to what it is** — in the function name, the field name, the
   GUI column header and the TSV column together — and stop naming Doench.
