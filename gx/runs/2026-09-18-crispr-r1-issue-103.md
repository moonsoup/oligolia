Found by the `oligolia-gx-tests` differential round on CRISPR (round 1). Not fixed here — this is a report, with a sealed failing test attached.

## Symptom

The CRISPR panel offers four nucleases. Select **SpCas9-HF1** and the panel's own
description line says (`gui/panels/crispr_panel.py:24`):

> NGG PAM · high fidelity · fewer off-targets

Run the same target with off-target checking on, once as SpCas9 and once as
SpCas9-HF1. The two responses are **field-for-field identical**: same
`total_candidates`, same ten guides in the same order, same positions, same
on-target scores, same off-target summaries, same specificity scores.

The description makes a claim specifically about off-target counts. That is the one
number the app does compute, and it comes back unchanged.

## Requirement

**CR-12** (`gx/crispr/register.json`):

> SpCas9-HF1 is offered as a distinct nuclease in the CRISPR panel's Cas-type list and described there as 'NGG PAM · high fidelity · fewer off-targets'. Selecting it must therefore change something the user can see: for the same target with off-target checking on, the SpCas9-HF1 response must not be field-for-field identical to the SpCas9 response. Either the specificity model differs, or the option is a label over the same computation and the description is false.

This requirement needs no external authority — the app's own Cas-type description is
the claim under test. The test imports `CAS_INFO` from the GUI and asserts the
promise is still there before checking the behaviour.

## Differential evidence

Two inputs, `check_off_targets=True`, `max_guides=10`, guide length canonical (20),
called in-process as `gui/panels/crispr_panel.py:_run_design` calls it. Compared
fields: the full `GuideRNA` model dump of every returned guide, plus
`total_candidates`.

| input | `total_candidates` (both) | guides identical | specificity scores (both) | off-target counts (both) |
|---|---|---|---|---|
| `gx/corpus/inputs/puc19_L09137.2.txt` | 326 / 326 | yes, all 10 | `[100.0]` | `[0]` |
| `gx/corpus/inputs/NG_007400.1.gb` | 5409 / 5409 | yes, all 10 | `[95.6, 97.7, 100.0]` | — |

There is no field in the response — not one — whose value depends on which of the
two nucleases was selected.

## Where it is

- `backend/routers/crispr.py:102` — the design branch is
  `if cas in (CasType.CAS9, CasType.CAS9_HF):`. SpCas9-HF1 never diverges from
  SpCas9 anywhere inside it.
- `backend/routers/crispr.py:196` — the off-target scan hardcodes the family:
  `cas_family = "cas12a" if cas == CasType.CAS12A else "cas9"`, so HF1 gets the plain
  SpCas9 model.
- `backend/routers/crispr.py:57-71` — `CANONICAL_GUIDE_LENGTH` and `PAM_LENGTH` give
  `CAS9_HF` the same 20 / 3 as `CAS9`, which is correct and not the issue.
- `gui/panels/crispr_panel.py:22-27` — `CAS_INFO`, where the promise is made.

So the option is a label over a computation that cannot distinguish the two.

## What a fix would have to choose between

Either

1. give the specificity model a high-fidelity variant — HF1's documented behaviour
   is a sharp reduction in tolerated mismatches, so at minimum it should not report
   the same off-target set and specificity as wild-type SpCas9 (note that the
   specificity number itself is currently position-blind; see the CR-11 issue, which
   is a separate root cause and would want fixing first or alongside); or
2. stop promising one — change `CAS_INFO["SpCas9-HF1"]` so it no longer says
   "fewer off-targets", and say plainly in the UI that the two are scored
   identically.

Shipping both the promise and the identical computation is what makes this a defect
rather than a missing feature.
